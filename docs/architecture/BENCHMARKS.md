# Active benchmark specification

Status: proposal for owner review, not authorization to run tests. This specification supersedes conflicting transport and workload assumptions in the historical [Phase 0C proposal](../archive/phase0/PHASE0C_BENCHMARK_PROTOCOL.md); that file and all historical evidence remain unchanged. No hardware benchmarks were executed for this specification. All numerical limits are candidates pending validation and owner approval.

## Preconditions and evidence

Run only after explicit test-window and device authorization, on a real Pi 4B 1 GB and physical iPhone, separately for dedicated and shared profiles. Record commit, time, hardware, OS/kernel, firmware, browser, compositor, iOS, BLE adapter, power/cooling, display, network, provider, lawful content, observable codec/resolution, workload, instrumentation and sample interval. Sanitize identifiers, credentials, QR secrets and typed content. Capture baseline and before/after health of existing services; obtain independent recovery. Missing metrics are unavailable, not passes. Record failures, aborts, sample counts, distributions and raw evidence location. Compare sampler overhead with and without instrumentation. Never alter unrelated services, swap, security controls or system configuration to obtain a pass.

## Cases and measurement

| Case | Method and proposed acceptance evidence |
|---|---|
| Keyboard-free acceptance | With prepared media and empty USB input ports, boot and complete candidate enrollment, normal control, controller management and recoverable application failure using TV and physical iPhone only, with no mandatory CEC or shared Wi-Fi. Exercise replacement with independently stored recovery proof, missing proof fail-closed, BLE-only operation, network setup and rollback, and preservation of shared workloads. Security approval and hardware authorization are prerequisites. |
| Idle and resources | Capture 10-minute host baseline and 5-minute core idle PSS/CPU; collect system MemAvailable at 5-second intervals, process PSS, cgroup current/peak/events, CPU per core, swap I/O, thermal and throttling, disk I/O and PSI where available. Do not sum RSS as PSS. Proposals: core ≤20 MiB PSS and ≤1% logical core idle, ≥100 MiB available for ≥95% steady playback samples, no OOM or sustained swapping. |
| Command latency | Correlate IDs from phone send to authenticated accepted and applied results separately; measure round trips on one clock or calibrate clock uncertainty for one-way measurements. Report p50/p95/p99, loss, failure/unknown and sample size, idle and during playback. Candidate p95 ≤100 ms for eligible discrete input accepted/applied RTT separately; applied denotes adapter boundary, not playback. State-query, lifecycle and pairing latency are distinct classes: measure distributions and establish thresholds after baseline, not a universal 100 ms completion target. Record timeout/failure counts and at least 100 samples for frequent input where practicable. |
| Reconnect | Repeatedly disconnect, radio-off/on and return to foreground in range during playback; measure recovery to authenticated authoritative snapshot and p50/p95/p99, failure and attempts. Candidate p95 ≤5 s under declared conditions; verify no stale command replay and held keys released. |
| Pointer and discrete load | Continuous pointer and scroll with measured input-to-observed response, coalescing and bounds; candidate pointer p95 ≤150 ms. Burst rapid ordered clicks/keys across saturation; record admitted, busy, applied, failed and unknown. Accepted discrete commands must not silently disappear; ordering around motion and click must hold. |
| Backpressure and memory | Exercise smallest negotiated payload, slow receiver, concurrent fragments, malformed lengths and bounded queues. Measure peak per-peer and global memory and time to recovery. Verify explicit busy/rejection and no unbounded allocation or false success. |
| Coexistence | Repeat control and playback cases with Ethernet, 5 GHz Wi-Fi and 2.4 GHz Wi-Fi separately, recording actual band, signal and interference; compare latency, loss, reconnect, throughput and failures. Measure useful BLE payload throughput in both directions under sustained bounded load. |
| Provider playback | Evaluate YouTube, Netflix, Spotify and Jellyfin with licensed content and record verified/degraded/unsupported/untested; do not bypass DRM. For video, propose stable 720p30 floor and 1080p30 target; report actual observed frames, codec and dropped-frame counters (<1% candidate after warmup), audio, login and limitations. Three ≥15-minute runs per viable scenario and 2-hour provider trials are proposed. |
| Lifecycle and workloads | Propose cold boot ≤45 s from power-on to actionable launcher or enrollment screen and return Home ≤5 s from command to actionable launcher. Measure 30 app switches, PSS/renderer/process cleanup and bounded resource growth (no orphaned process or uncontrolled trend), browser recovery and HDMI reconnect. Require no unexpected project process restart during stable playback. Record exact endpoints, sample count and exceptions. Repeat representative playback and control while owner-approved existing workloads run; compare service availability, latency and throughput against baseline. No shared-host support claim from idle-only tests. |
| Reliability | Following short-run gates and separate authorization, run integrated 24-hour session with switching and reconnect; release gate proposes 72-hour reliability run. Record interruptions, recovery, resource trend and all unavailable observations. |

Candidate launcher initial compressed JS ≤200 KiB; report uncompressed bytes and parse/runtime costs. Candidate regression gate is ≤10% increase in core memory, CPU and latency versus a validated comparable baseline, or a reviewed ADR and new baseline; all absolute gates still apply. These are not guarantees.

Optional candidates: 1080p60 stretch, not MVP floor; ZRAM comparison on an isolated approved environment only (no shared-host swap changes); iOS 18 candidate minimum pending actual OS/SDK and physical-device validation. Report unsupported or deferred options explicitly. See [test strategy](../engineering/TEST_STRATEGY.md).

## Abort and recovery

Before any shared-host run, agree owner-approved thresholds and stop authority. Proposed stops: any existing service degradation or unexpected restart; any host/cgroup OOM event; MemAvailable <64 MiB once or <100 MiB for two consecutive 5-second samples; sustained swap activity or pressure; current undervoltage/throttling or 75°C; repeated stutter, loss of control or unrecoverable browser/display failure; disk free space down >5% or I/O wait >20% for three samples. If a signal is unavailable use declared conservative substitutes, never infer health. Stop project workload only, return to local launcher if safe, preserve unrelated services, capture sanitized read-only diagnostics and record the abort. Do not reboot, modify host settings or retry until cause and recovery are reviewed. Benchmarks must not proceed without an independently usable recovery path.
