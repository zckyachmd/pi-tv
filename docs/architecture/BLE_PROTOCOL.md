# BLE protocol candidate v1

Status: proposed specification, not an interoperable wire standard or approval to implement production pairing. Owner-directed BLE and QR; UUID values, serialization, authenticated handshake and exact wire encoding remain unresolved implementation blockers. Limits below are testable candidate ceilings, subject to measurement and security review.

## Roles and discovery

Pi peripheral exposes a vendor 128-bit service; iPhone central scans, selects, connects, subscribes and writes. Advertise only service UUID and non-secret hint; address, name, hint and RSSI never authenticate. Info read is untrusted version/capability hint. RX writes with response carry bounded fragments; TX notification or indication carries fragments, with explicit delivery/backpressure verified on both systems. Characteristic write success only confirms GATT processing, not application admission. UUIDs must be assigned and recorded before interoperability; don't use unassigned SIG values. Use measured write length and notification limits, not a fixed MTU. Verify BlueZ adapter/advertisement capacity, privileges, coexistence and service lifecycle on target.

## Enrollment and session

Candidate QR structured payload: `{format:1, device_hint, identity_public_key_or_fingerprint, enrollment_secret, expiry_or_window_id}`; exact encoding, bounds, clock semantics and key format depend on selected secure protocol. Secret is CSPRNG-generated, at least 128 bits if the selected construction permits, unique, used only for this enrollment, never advertised or logged. Device enforces its own monotonic deadline (candidate 120 s); client expiry display is informational when clocks differ. Physical local action opens enrollment; locally confirm the peer before granting persistent trust. Phone authenticates Pi against QR; Pi authenticates possession of enrollment authorization and client identity; bind both identities, version, roles and negotiated parameters to the authenticated transcript. OS bonding is independent defense in depth and not enrollment.

States: idle → open → connected → authenticating → awaiting-local-confirmation → committing → enrolled; cancel, timeout, failure, crash or reset → idle with secret invalidated. Commit peer and consume secret atomically; if crash outcome is uncertain reject old QR and require fresh enrollment. Cap attempts and concurrent handshakes without allowing permanent attacker-triggered lockout. No unauthenticated fallback. Reconnect mutually authenticates fresh session with enrolled credential, checks revocation and negotiates authenticated version. Revoke persists before reporting success, closes active session and denies future sessions; identity reset invalidates all peers. Key rotation and recovery need reviewed migration before release.

## Secure-channel options — unresolved

| Candidate | Evidence and tradeoff | Gate |
|---|---|---|
| TLS 1.3, Rust rustls + SwiftNIO SSL | [rustls features](https://docs.rs/rustls/latest/rustls/manual/_04_features/index.html) support TLS 1.3 and client authentication; [SwiftNIO SSL](https://github.com/apple/swift-nio-ssl) provides TLS handlers. Both describe streams/channels, not a proven CoreBluetooth byte-stream integration. Certificate pinning, mutual identity, one-use enrollment, memory and reliable bounded framing remain to be designed. Disable 0-RTT for commands. | Demonstrate bounded stream adapter, interop, identity pinning and independent security review. |
| Noise framework, Rust Snow + a Swift implementation | [Noise specification](https://noiseprotocol.org/noise.html) defines patterns; [Snow](https://github.com/mcginty/snow) implements Noise but explicitly reports no formal audit. A maintained, compatible Swift implementation and exact enrollment/reconnect pattern are not selected. | Verify maintenance, independent review, interoperability, transcript binding and protocol pattern. |

Reviewed 2026-11-27. Neither option is validated or selected. Do not create bespoke cryptography or use a generic HMAC challenge as a substitute. Security review must specify identity lifecycle, channel binding, cryptographic suite, key storage and cross-language test vectors. If no sound maintained interoperable stack exists, production pairing is blocked.

## Framing, flow and limits

Candidate logical record header contains framing version, message ID, fragment index, total fragment count and declared total length; exact byte order/encoding reserved until the selected secure channel and minimal ATT payload are validated. Validate every field and actual received length before allocation. Max logical message 4096 bytes, 2 in-flight per peer, 3-second reassembly timeout; reject duplicate/conflicting, missing, out-of-order and oversized fragments, and discard on disconnect. Bound total allocation globally, including unauthenticated peers. Authenticate complete record and security-relevant framing context using the chosen protocol; never execute partial plaintext. Fragment ACKs cannot substitute for authenticated application results. Test fragmentation at smallest negotiated payload, counter exhaustion and malformed lengths. Limit connections to one active controller and candidate five enrolled identities; second controller receives busy, no silent takeover.

Candidate application envelope `{version, session_id, sequence, id, kind, generation, payload}` is authenticated, with strict types, bounded strings and unknown-field policy fixed with encoding. Version major must match; minor features are negotiated as an authenticated intersection and unknown required features fail closed. Sequence is monotonically increasing per direction and replay checked; no wrap (rekey/reconnect first). Request IDs are unique per session, cached within bounded lifetime; duplicate receives same known result and never re-executes. Across session loss, no exactly-once guarantee: report unknown and resnapshot, never automatically replay non-idempotent operations. Snapshot carries monotonic state revision and runtime generation. State deltas include base revision; gaps request snapshot.

Candidate command kinds: `app.launch`, `app.close`, `app.restart`, `input.key`, `input.text`, `input.pointer.move`, `input.pointer.click`, `input.scroll`, `media.play`, `media.pause`, `media.seek`, `media.next`, `system.home`, `system.volume.set`, `system.volume.mute`, plus `state.get`, `capabilities.get`. Exact key enums, text length, numeric ranges and timeout rules must be fixed in fixtures before implementation. Admission checks authorization, state, generation, capability and queue. `accepted` means queued; `applied` means runtime confirms the documented adapter boundary, not that a provider actually played media; `failed` or `unknown` is explicit. Accepted does not survive daemon failure. Bound discrete queue (candidate 32); reject with busy, never silently drop accepted discrete commands. Coalesce unsent pointer/scroll deltas at candidate 30 Hz, preserve ordering around click/key events, use bounded accumulated values; never coalesce discrete controls. Release held keys on disconnect.

Error codes: `UNAUTHENTICATED`, `FORBIDDEN`, `EXPIRED`, `REVOKED`, `WRONG_DEVICE`, `VERSION_UNSUPPORTED`, `INVALID_MESSAGE`, `TOO_LARGE`, `RATE_LIMITED`, `BUSY`, `STALE_GENERATION`, `UNSUPPORTED`, `TIMEOUT`, `UNAVAILABLE`, `INTERNAL`, `OUTCOME_UNKNOWN`; avoid exposing secrets or sensitive peer details. Define retryability per operation: busy may retry with backoff; unknown outcome requires state reconciliation. Advertised capabilities are hints; authenticated snapshot reports actual supported/unsupported/unknown and revision. Never trust requested manifest capabilities as grants.

Tests: malformed/fragment fuzzing, minimum payload, truncation/duplicates, reordering, flood and memory bounds; replay/downgrade, rogue device, stolen/expired QR, identity mismatch, revoke during session, crash at each commit step, response loss and duplicate commands; radio off, permission denied, foreground recovery, Wi-Fi coexistence and no-shared-IP physical test. [Apple write length](https://developer.apple.com/documentation/corebluetooth/cbperipheral/maximumwritevaluelength%28for%3A%29) is per write type; [BlueR GATT example](https://docs.rs/bluer/latest/bluer/gatt/local/struct.CharacteristicNotifier.html) demonstrates an API, not target capability. Reviewed 2026-11-27.

## Boundary clarification and interoperability gate

1. **BLE transport and fragmentation:** GATT provides untrusted bounded fragments and flow-control events. Its acknowledgments are not secure-channel or application acknowledgments. The TLS candidate requires a reliable, ordered, bounded byte-stream adapter with defined loss, disconnect and backpressure behavior; GATT notifications alone do not establish this property.
2. **Authenticated secure channel:** TLS 1.3 over that stream and Noise remain unresolved candidates. It authenticates and protects the negotiated transcript and bytes; neither framing nor OS bonding grants application authority. Library availability, maintenance, licensing, Swift/Rust interoperability, memory and channel binding are blockers.
3. **Application session and authorization:** bind the authenticated identity to enrollment or a revocable credential, negotiate versions, enforce replay/sequence, access policy and session limits, and reconcile state on reconnect. The local authorization ceremony is specified in [recovery](RECOVERY.md).
4. **Domain commands and state:** transport-independent typed requests, results, capability and revision semantics are owned by the domain contract; they must not depend on GATT, a chosen secure channel or UI framework.

Session 2 evaluation requires independent security review and reproducible cross-language fixtures, negative and downgrade tests, bounded stream/framing tests at minimum negotiated payload, credential lifecycle/crash tests and measured resource overhead. Selection requires owner approval after review; no algorithms or production implementation are selected here. The candidate fragment header above may need revision for a stream adapter and must be authenticated as appropriate to the selected design.
