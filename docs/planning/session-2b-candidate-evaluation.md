# Session 2B.1 — secure-channel candidate decision

**2026-11-27 · Review gate: experimental recommendation, not admission or implementation.** Recommend TLS 1.3 using rustls and SwiftNIO SSL for a bounded host-only interoperability experiment, subject to owner approval of the dependency set below. This is a candidate selection, not evidence that the libraries interoperate here, that the GATT adapter is reliable, or that F-23 is complete. Independent security review is required before production and before the reviewed experiment advances as required by the runbook. No dependency was installed or manifest changed. Session 2A's [conditional closure](session-2a-completion.md) carries open measurements and BLE-21/BLE-23 prerequisites.

## Comparison and upstream evidence

| Candidate | Assessment |
| --- | --- |
| TLS 1.3: rustls + SwiftNIO SSL | **Recommend for experiment.** Both implement standard TLS 1.3 and support certificate-based mutual authentication. Rustls exposes caller-driven `read_tls`, `process_new_packets`, and `write_tls`; SwiftNIO SSL is a BoringSSL-backed NIO channel handler, and NIO offers `EmbeddedChannel` for externally driven byte buffers. Neither requires the experiment to open TCP sockets. An embedded channel is a test facility, not proof of a safe asynchronous BLE bridge. [rustls API](https://docs.rs/rustls/0.23.46/rustls/struct.ConnectionCommon.html), [NIO SSL](https://github.com/apple/swift-nio-ssl/tree/2.37.8), [NIO Embedded](https://github.com/apple/swift-nio/tree/2.105.2/Sources/NIOEmbedded). |
| Noise: Snow + Swift Noise | **Do not admit now.** `Noise_XX_25519_ChaChaPoly_SHA256` is a plausible three-message mutual-static-key pattern if both learned static keys are checked against independently provisioned pins after handshake; a fixed prologue binds protocol/version and the handshake hash binds the transcript. Fresh ephemerals yield fresh keys; stateful AEAD nonces and strict sequencing reject replay within a session, while fresh handshakes prevent cross-session replay. A fixed suite, no fallback, bounded record framing and fail-closed loss handling are still required. [Noise specification](https://noiseprotocol.org/noise.html), [Snow 0.10.0](https://github.com/mcginty/snow/releases/tag/v0.10.0). |

Snow 0.10.0 supports named patterns/suites and requires Rust 1.85. [swift-libp2p/swift-noise](https://github.com/swift-libp2p/swift-noise) claims XX, X25519, ChaChaPoly and SHA-256 and official vectors; its repository was updated in August 2026, but its small project history and claims alone do not establish sustained security maintenance, audit, iOS deployment compatibility or Snow interoperability. [trancee/noise-protocol](https://github.com/trancee/noise-protocol) claims matching patterns and iOS 16, but is a young project with no established independent review found; [Torann](https://github.com/stonygrey/torann) is also young and requires iOS 18. [OuterCorner/Noise](https://github.com/OuterCorner/Noise) last pushed in 2024. These are leads, not proof that no viable Swift implementation exists. No Snow or Swift Noise package is proposed for admission. Do not implement Noise primitives or a bespoke Noise handshake. If reconsidered, a record adapter needs one bounded Noise ciphertext per ordered record, sequence/loss detection and backpressure in both directions, with authentication failure tearing down the session; exact maximum plaintext must account for the AEAD tag.

## Transport and adapter

The [Phase 2A transport](../../prototypes/phase2a-ble/transport/README.md) has a 13-byte fragment header, contiguous record IDs per fresh connection, strict ordered fragment reassembly, expiry and bounded declared payload reservations. The integrated echo sends one record per direction, writes with response one at a time and handles notification submission backpressure. Deterministic fixtures and matching physical echoes establish those tested cases; GATT write response acknowledges a write, and accepted notification submission **does not prove receipt**. An ID gap detects a wholly lost record only when a later record arrives; loss of the final record is invisible without an acknowledgement, deadline or explicit close. The echo's matching response is specific to request/response and is not general bidirectional stream delivery.

For TLS, replace the echo path in a future experiment with one bounded full-duplex ordered byte-stream adapter per connection. Chunk arbitrary TLS ciphertext into ordered logical records of at most 4096 bytes; a TLS record or handshake flight may span multiple chunks and receives must concatenate bytes without interpreting TLS boundaries. Add per-direction receipt acknowledgements and bounded credit/window flow control, including for an otherwise idle peer, with finite delivery deadlines. Advance/release only on validated delivery acknowledgement; never silently skip, replay or repair ambiguous data. Bound pending chunks, byte queues, certificate/handshake inputs and total per-peer/global allocation, including framework and TLS buffers; set explicit test limits and fail closed on exhaustion. Drive rustls I/O and a Swift NIO channel from the external byte stream; propagate malformed frames, gaps, timeout, backpressure failure and disconnect as terminal errors to TLS and discard all session state. The host harness must inject both directions independently and test a lost final record as well as middle loss.

On orderly close require authenticated TLS `close_notify` and drain within a deadline; a disconnect or EOF without it is truncation, never successful completion of a partial application message. Unauthenticated framing acknowledgements do not establish peer identity or protect availability; an attacker can force a failure, not gain authorization. Same-peripheral late callbacks and reconnect generation remain unresolved. Physical use requires BLE-21 and BLE-23 fixes and verification first, and must establish these guarantees rather than assume them. This is a proposed adapter, not an implementation or a claim that the current transport can directly carry TLS.

## Synthetic security construction

Use a synthetic test CA and two short-lived test leaf certificates with appropriate server/client usages and distinct identities; no real keys or durable store. Configure iPhone as TLS client and Rust as server, require and validate client certificates and server chain, validity, intended usage and a fixed test server name. Enforce an expected peer leaf certificate or SPKI pin **in addition to** valid chain/identity checks in both directions before delivering application data. Verify the exact version-specific callbacks support this safely: SwiftNIO's [custom verification callback](https://github.com/apple/swift-nio-ssl/blob/2.37.8/Sources/NIOSSL/SSLCallbacks.swift) can replace all built-in verification, so an accepting custom callback is not a substitute for chain validation. If safe combined validation/pinning is unavailable, the experiment is blocked pending review rather than disabling validation. Pins and certificates are fixture inputs; rotation, revocation, clock failure and recovery of real identities remain Session 2C/product design questions.

Require TLS 1.3 only, a fixed application protocol/version identifier via ALPN and transcript-bound handshake, mutually authenticated peers and fresh full handshakes with resumption/tickets and 0-RTT disabled. Verify those settings on both libraries; TLS transcript authentication binds negotiated parameters, not any unbound external metadata. Start no application data before authentication and protocol selection complete. Generate new session keys each connection, reject old ciphertext, identity mismatch, invalid/expired certificates, unsupported protocol/version, malformed data and unexpected EOF; never fall back to plaintext or an unauthenticated mode. Set finite handshake time, per-flight and aggregate byte limits and cancellation; ensure library buffering is covered, not only the outer queue. Test exhaustion and timeouts, not merely configuration values.

A CoreBluetooth identifier routes an unauthenticated connection. A validated certificate and pin identify a cryptographic peer. Application authorization decides what that identity may do; a controller lease arbitrates control separately. This experiment grants neither ownership nor a real lease, executes no commands, and implements no enrollment, recovery or trust store. Availability attacks, compromised endpoints/keys, relay and physical proximity are outside what the TLS handshake alone solves.

## Bounded Session 2B.2 after approval

1. Resolve and audit the exact experimental graph, pin lockfiles and implement only an isolated synthetic in-memory Rust–Swift TLS harness. Do not access hardware, alter production manifests or use real credentials.
2. Demonstrate both directions and fresh independent sessions, TLS 1.3/ALPN/mutual certificate and pin enforcement, no 0-RTT or resumption. Exercise wrong/missing pin, rogue/expired/missing certificate, wrong name/usage, version/ALPN mismatch, replay, malformed/truncated ciphertext, close without `close_notify`, loss, duplicates, reordering, stalls and resource/time caps. Ensure failures produce no application success or plaintext fallback.
3. Exercise bounded chunk transport with >4096-byte handshake flights, simultaneous backpressure and lost final chunk using deterministic fault injection. Measure handshake and data bytes, latency, buffer high-water marks, binary size and process memory on host; separately record target measurements as untested. Independent security review and owner disposition remain necessary before any 2B.3 physical integration. F-23 requires interop, negative tests and review; this document alone does not pass it.
