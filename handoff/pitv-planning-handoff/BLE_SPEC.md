# BLE remote transport & security — specification candidate

## Roles and scope
Pi = BLE peripheral, GATT server and advertiser; iPhone = central/GATT client. Bluetooth 5/BLE exists on Pi 4 hardware; verify BlueZ adapter peripheral/advertising capabilities, firmware, permission and coexistence under 2.4 GHz Wi-Fi. Use standard CoreBluetooth (not Bluetooth Classic serial/SPP or HID emulation). QR is application enrollment, not a mechanism for silently forcing OS Bluetooth bonding. Never use MAC address, advertised name, RSSI or UUID as identity proof. Native OS pairing/encryption can provide defense in depth; iOS/BlueZ behavior needs testing. Do not advertise secrets. No streaming media over BLE.

## Candidate GATT profile
Generate stable project-specific 128-bit UUIDs only after checking collision policy; assign in contracts and test fixtures. Do not invent a Bluetooth SIG assigned number. One service with minimum characteristics:
- Info (read): protocol versions and bounded non-sensitive device label/capability hint; untrusted until authenticated.
- RX (write with response): enrollment/handshake and discrete encrypted command fragments.
- TX (notify/indicate as appropriate): encrypted replies, state/events and handshake fragments. Verify subscription and backpressure.
- Optional fast input characteristic (write without response) only if benchmark requires and secure flow-control/drop semantics are validated. Never use for irreversible/discrete commands.

Use actual `maximumWriteValueLength(for:)` on iOS and measured BlueZ negotiated limits. Never assume 512 bytes or fixed MTU. Define versioned framing: message type, fragment index/length, message ID, total length; all limits checked before allocation; authenticate complete logical record and relevant framing context; no untrusted fragments executed. Candidate max 4 KiB logical message, max 2 in-flight per peer, bounded buffer, 3 s reassembly expiry; test minimal ATT payload and Unicode split, duplicates, missing/out-of-order fragments, disconnect and hostile sizes. Exact format/limits require ADR and interoperability tests. No compression initially. Transport ACK != authorization != command accepted != applied. Explicit result codes; sequence/replay protection; new session on reconnect; deduplication of retryable commands and safe timeout handling. Coalesce pointer/scroll deltas (candidate <=30 Hz adaptive), rate-limit text/discrete commands, avoid periodic high-rate state polling. Backpressure, cancellation and no unbounded queues. P0 one active controller; persistent known-device roster bounded (candidate 5); second controller gets busy/handoff UI, never steals session silently.

## Pairing and security
Threats: rogue peripheral, nearby unauthorized central, MITM, replay, captured/reused QR, malicious fragmentation, BLE flood/battery drain, stolen phone, local hostile site, untrusted Linux process, accidental leakage in evidence. Radio jamming/relay proximity guarantees out of scope; document residual risk.
1. Physical pairing mode from trusted launcher or explicitly authorized local CLI recovery. Window e.g. 120 s. Pi generates device identity at first provision and CSPRNG one-time enrollment secret (candidate >=128 bits; satisfy chosen protocol's exact PSK length). QR contains protocol version, non-secret device hint, Pi public identity key/fingerprint and expiring secret. No URL analytics, network transfer or screenshot in evidence. Never use six-digit code directly as a cryptographic key.
2. iPhone scans QR, validates bounded syntax/version, discovers matching service and connects. It authenticates Pi identity against QR using an established reviewed authenticated key exchange; both prove enrollment authorization. TV shows explicit confirmation/short fingerprint as UX defense where appropriate. Expire/consume secret atomically after successful enrollment, limit attempts; never accept arbitrary central because it is bonded.
3. Establish confidential, authenticated, replay-resistant session using a vetted standard protocol and audited interoperable libraries. Evaluate TLS 1.3 over a reliable bounded BLE byte-stream vs an appropriate Noise handshake with authenticated static keys and one-time PSK. Noise pattern/cipher suite, transcript binding, identity pinning, enrollment vs reconnect, forward secrecy, key rotation and library availability on Swift/Rust require a reviewed security ADR; do not implement own crypto, ad hoc challenge/HMAC protocol, or ship unauthenticated fallback. If neither can be safely implemented, BLOCK rather than silently weaken.
4. Persist authorized peer identity/credential in Pi owner-only store and iOS Keychain (device-bound accessibility where appropriate). Store no reusable credentials in logs, plaintext preferences or QR history. Subsequent connections mutually authenticate with fresh session keys; reject downgrade, replay, wrong device and revoked identities. Provide explicit device removal, factory reset, lost phone recovery and bounded reconnect backoff. Persist changes atomically and document backup/rotation. OS bond removal policy separate; do not alter unrelated bonds.
5. Use session-scoped authorization and capability checks before dispatch; do not expose raw CDP, shell, filesystem, host shutdown, arbitrary URL or JS endpoints. Clear incomplete frames/pressed keys on disconnect. BLE link loss must leave playback running; UI transitions to disconnected; restore authoritative state on reconnect.

## Evidence & tests
Host-first: mock transport tests for framing, permissions, session state and protocol; physical iPhone -> Mac peripheral controlled spike with Wi-Fi/cellular off (phone Bluetooth on). If Mac peripheral unavailable, report BLOCKED, use authorized Pi BlueZ spike later. Simulator does not prove actual radio, permissions or bonding. Test phone Bluetooth disabled/denied, QR camera denied, malformed/expired/replayed code, wrong Pi, unauthorized/revoked peer, tampering, duplicate commands, min MTU, oversize, flood, disconnect during handshake/command, reconnect, background/foreground/lock, process restarts, adapter off/on, multiple nearby devices, coexistence with streaming Wi-Fi. Do not claim background availability; foreground remote sufficient for MVP. Explicitly test no shared IP network and no mobile IP listener. Proposed latency test >=100 commands per scenario with monotonic timestamps and measured end-to-end applied vs ACK; report p50/p95/p99, losses and conditions. Measure BLE CPU/RAM delta and impact on playback and existing services on real Pi. Security review is mandatory before production enrollment.
