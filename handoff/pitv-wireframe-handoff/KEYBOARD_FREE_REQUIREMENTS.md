# Owner direction — no additional input peripherals

Baseline reviewed: `8989129221a08035b226b95f431238b7db8540f6` on `main`. The owner explicitly requires the appliance to be usable with a supported single-board computer, a TV and an iPhone, without an additional keyboard, mouse, controller, GPIO button, or mandatory HDMI-CEC. Power, storage containing an installed OS/application, HDMI cable and TV input selection are inherent prerequisites. Internet on the Pi is needed for online services, not the BLE remote. A Mac or separate host is a development/provisioning tool, not an end-user operating requirement. Raw/unprovisioned boot media and fatal OS/storage/radio faults cannot be guaranteed recoverable by these three devices alone.

## Requirement changes for Codex

- R-01: on a pre-provisioned reference appliance, boot automatically to local launcher/enrollment without keyboard, mouse, TV remote as input to Pi, SSH, manual IP or shared network. Select HDMI input using TV's own controls/previous selection; do not require CEC support.
- R-02: initial trusted enrollment must be initiable and completable using TV display and iPhone only; QR-bound authentication and explicit informed phone confirmation; no action on Pi/TV launcher requiring prior remote. The former separate trusted local input confirmation is superseded as a requirement, not removed from security considerations without review.
- R-04/R-23: normal operation, adding/revoking controllers, replacement iPhone, all controllers unavailable, logical reset and recovery must have phone-based authorized workflows. Require independent owner proof for recovery, not radio proximity or an unowned bootstrap QR on an owned device.
- R-05: remote includes D-pad, pointer, click, scroll, text (iPhone native keyboard), system/available audio volume, back, Home, capability-dependent media. No attached HID required, including provider sign-in where supported.
- R-08/R-20: automatic bounded restart/recovery of appliance processes and display; recover via authorized phone while OS/radio is functioning. Fatal faults and loss of every credential use a separate documented maintenance/re-provisioning path, not a silent trust bypass. Shared host must not be rebooted or have unrelated settings changed automatically.
- New acceptance requirement: provision Pi internet optionally from authenticated iPhone BLE session (network configuration adapter, least privilege, owner approval, rollback); Ethernet alternative; shared-host network mutation disabled unless separately authorized. Offline launcher and pairing must still work. Do not log Wi-Fi credentials or send them outside authenticated protected channel. No LAN fallback.
- Distribution: pre-provisioned image or documented installer/preparation on an existing OS is a required public appliance onboarding deliverable (previously deferred image must be reconsidered). Native `.deb` remains packaging source; do not distribute cloned device keys or proprietary CDMs without permission. No claim that iOS can flash all Pi boot media itself.

## Proposed security model — not ratified

### 1. Initial ownership

Unowned appliance (durable state) automatically shows a short-lived single-use QR challenge on its own HDMI display; it can advertise a non-secret hint. QR contains the Pi's cryptographic identity anchor and high-entropy enrollment authorization. The phone authenticates the device to that anchor *before* transmitting any sensitive enrollment material; proof of QR authorization and fresh client identity are bound to the reviewed mutual-authentication transcript. Candidate UI shows a transcript-bound human-verifiable phrase on both screens; exact cryptographic method and entropy are unselected. The human confirms on iPhone after physically comparing the displayed values. Only success from the durable ownership commit permits authenticated synchronization/Ready. Atomically consume authorization and establish first owner, reject concurrent/racing enrollments, clear QR, and persist an owned marker across restart. Cancel, expiry, ambiguous commit, and power loss fail closed. Never enter unowned state on corruption.

This uses possession of an on-screen enrollment secret as initial authorization; it is **not** independent physical input or proof of distance. An attacker who can photograph the QR may race the legitimate owner; comparison alone cannot solve that. Explicitly assess shoulder-surfing, relay, unauthorized observation, races, bounded attempts and enrollment-window renewal. For a never-owned appliance, automatic renewal of bounded one-use QR windows may be considered only under a reviewed unowned bootstrap policy; no such renewal on an owned device without authenticated authorization. Do not invent custom crypto, accept bonding alone, or claim this ceremony secure before an independent review and cross-language/physical tests. If no acceptable model can be validated, mark production blocked rather than restoring mandatory HID or weakening security.

### 2. Owned device

Authenticate existing enrolled phone and authorize actions by a minimal owner/controller policy; do not imply every controller has owner authority. An owner may open and explicitly approve an additional enrollment on their already trusted phone; the joining phone scans temporary TV QR and verifies identity. No extra input hardware required; reject if owner authorization is absent. Atomic revoke and terminate sessions. Reset remote access and rotate identity only through a separately reviewed authenticated owner/recovery action with explicit scope; preserve provider profiles by default. No factory reset from untrusted BLE commands. Owned device never automatically displays an open ownership enrollment QR on disconnect, timeout, restart or BLE loss.

### 3. Replacement/lost phone

Proposed recovery kit: a high-entropy recovery credential plus device identity anchor, created after initial ownership and backed up somewhere accessible independently of that iPhone (e.g. owner-managed secure password vault or encrypted recovery export, not a service dependency). Never put actual secrets in screenshots/logs/advertisements/general UI state. The replacement iPhone can discover via BLE hints and authenticate the device using the saved identity anchor, then prove the recovery credential via the reviewed secure protocol, without requiring a prior active controller or an action on the TV. Consider bounded, authenticated display verification after proof; no unauthenticated request may disrupt playback or trigger destructive action. On success atomically establish replacement authority, invalidate recovery credential and rotate it; revoke lost controllers with explicit policy (proposed default revoke previous controllers for all-lost recovery); preserve provider profiles unless explicit authorized erase. Recovery kit storage, verification, rotation, backup and crash semantics are security-review blockers. If a user loses both all trusted controllers and recovery proof, secure ownership recovery is impossible under this model; re-provision through an explicitly documented maintenance process, not an insecure reset or an assumption that every Pi has a hardware button. On fatal BLE/OS/media faults, supervisor recovery first; maintenance when needed.

## Evidence gates before implementation/release

- First boot from prepared media with all USB input ports empty; TV without reliance on CEC; physical iPhone Wi-Fi/cellular off, BLE on. QR, verification, expiry/renewal, concurrency, durable commit, wrong identity, stolen QR, repeat use, and no default insecure fallback.
- Full iPhone input, provider sign-in, network provisioning, reconnect, HDMI reconnect, browser failure, local control while Pi internet is disconnected. Existing shared workloads untouched. Existing independent maintenance/SSH access remains a developer safety prerequisite, not a customer dependency.
- Add/revoke, second controller BUSY, lost phone with recovery kit, wrong/replayed recovery kit, power loss, owner reset, profile preservation, missing recovery kit fail-closed. No stored credential reuse, untrusted takeover or unauthorized display disruption.
- Demonstrate actual physical iPhone/Pi, BLE interop/security review, 1 GB performance and HDMI/DRM playback. Keep all historical evidence unchanged. Do not claim this model is validated by these wireframes.
